# Excel upload validation

Feature 5 of the agreed security sequence. Implemented 2026-10-09.

## File handling

All import services and metadata reads now use the same bounded workbook opener. This covers student rosters, legacy single-LO uploads, LO attachments/replacements, bulk LO uploads, question uploads and the unified metadata-based upload.

- Accept `.xls` and `.xlsx` (including uppercase extensions), with supported Excel MIME types, generic binary type or an absent MIME type.
- Reject empty files, unsupported extensions/content types, and files whose signature does not match their extension. Apache POI must also successfully open the workbook; renamed text, corrupt archives and encrypted/unsupported workbooks get a controlled validation message.
- Keep the existing 5 MB per-file and 6 MB multipart-request limits. The HTTP multipart limit returns 413. Invalid workbook content returns 400, including validation during lecturer authorization metadata reads.
- Before POI opens an XLSX archive, limit its actual expanded content to 32 MB and its entries to 1,000. Reject duplicate entry names and OOXML macro/embedded-object entries. POI's own archive protections remain enabled.
- Once opened, limit workbooks to 16 sheets, 10,000 rows per sheet including headers, 256 columns per sheet, 200,000 populated cells overall, and 4,096 characters per text cell.
- Reject formula/error cells; users should paste calculated values before uploading. No formula evaluation is performed.

The frontend checks extension, empty files and the 5 MB size cap for file selection, drag/drop and upload-service submission. The forms show the supported types/limit and formula guidance. The backend remains authoritative for actual file contents and rows.

## Template and record validation

- Student rosters must have the five template headers in order: Student ID, Student Name, Email, Academic Year, Batch. Enforce identifier/name requirements, field lengths, basic email syntax, duplicate IDs and unexpected extra columns. Invalid rows reject the whole upload.
- Marks templates must have the expected student header and LO/question columns in order. Support the existing title/header layouts and old question templates with Student Name.
- Reject unknown students, duplicate IDs, populated rows missing IDs, extra columns, invalid numeric text, non-finite numbers, out-of-range scores and invalid maximum marks.
- Reject header-only files and marks templates with student IDs but no marks/attendance values. An unfilled template cannot clear previous marks.
- Preserve the existing attendance conventions: AB/MC/N/A and blank cells are skipped in bulk/question imports; legacy two-column imports treat attendance markers as zero and require a mark/marker for each populated row.
- Duplicate metadata keys are rejected. Metadata and service-level resource authorization continue to enforce the previous RBAC rules.

## Transaction behavior

Question scores are collected and validated before existing scores are deleted. Student imports roll back on checked exceptions as well as runtime errors. Every public legacy marks-import alias now enters a transaction.

The older Add Results replacement workflow previously sent a DELETE request before submitting its new workbook. It now sends `replaceBatch` with the upload. The backend performs replacement and attachment storage in one transaction; rejected content restores the old marks and attachment. Existing target-batch conflict checks still apply when moving to a different batch. No database migration is needed.
